# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 십자가(Cross)와 X 패턴을 판별하고, 패턴 크기(3×3 ~ 25×25)에 따른 연산 시간을 측정하는 Python 콘솔 애플리케이션입니다. NumPy 같은 외부 라이브러리 없이 표준 라이브러리만 사용합니다.

## 1. 실행 방법

### 요구 환경
- Python 3.8 이상 (개발·테스트 환경: Windows, Python 3.14.3)
- 외부 라이브러리 설치 불필요

### 실행
```bash
python main.py
```

실행하면 모드를 선택합니다.

| 입력 | 모드 | 사용 방법 |
|---|---|---|
| `1` | 사용자 입력 (3×3) | 필터 A, 필터 B, 패턴을 차례로 3줄씩 입력. 각 줄은 숫자 3개를 공백으로 구분 (예: `0 1 0`) |
| `2` | data.json 분석 | 경로 질문에서 **Enter**를 누르면 `main.py`와 같은 폴더의 `data.json`을 사용. 다른 파일을 쓰려면 경로를 입력 (예: `tests/bad_data.json`) |

### 테스트 실행
```bash
python -m unittest tests.test_main -v
```
표준 라이브러리 `unittest`로 작성한 테스트 63개가 실행됩니다.

### 프로젝트 구조
```
mini-npu/
├── main.py              # 메인 실행 파일 (섹션 1~9로 구분)
├── data.json            # 분석 대상 데이터
├── README.md
└── tests/
    ├── test_main.py     # 단위 테스트 63개
    └── bad_data.json    # 의도적 오류 데이터 (재현성 확인용)
```

## 2. 구현 요약

### 2-1. 데이터 구조
`Matrix` 클래스가 n×n 2차원 배열을 저장합니다. `get(row, col)`, `set(row, col, value)`로 특정 위치 값을 읽고 쓰며, 범위를 벗어나면 `IndexError`가 발생합니다. `Matrix.from_rows(rows)`는 2차원 리스트를 Matrix로 바꾸면서 정사각형 여부와 숫자 여부를 검증합니다.

### 2-2. MAC 연산
`mac(pattern, filter)`는 이중 `for`문으로 같은 위치의 값을 곱하고 누적합니다. 크기가 다르면 `ValueError`를 발생시키고, 결과는 항상 `float`입니다. 곱셈 횟수는 정확히 N²번입니다.

### 2-3. 라벨 정규화
data.json의 라벨 표기가 위치마다 달라서, 프로그램 내부에서는 표준 라벨 `Cross`, `X` 두 가지만 사용합니다.

| 원본 위치 | 원본 값 | 표준 라벨 |
|---|---|---|
| 패턴 `expected` | `+` | Cross |
| 패턴 `expected` | `x` | X |
| 필터 키 | `cross` | Cross |
| 필터 키 | `x` | X |

`normalize_label()`은 앞뒤 공백을 제거하고 소문자로 바꾼 뒤 매핑표로 변환합니다. 그래서 `" X "`, `"CROSS"` 같은 변형도 처리하며, 알 수 없는 값(`"?"`)이나 문자열이 아닌 값은 `ValueError`로 거부합니다. 모든 콘솔 출력과 PASS/FAIL 비교는 표준 라벨 기준으로 수행합니다.

### 2-4. 동점 처리 정책 (epsilon)
`compare(score_a, score_b)`는 `abs(score_a - score_b) < 1e-9`이면 동점으로 판정합니다. 동점 검사를 크기 비교보다 **먼저** 수행해서, 부동소수점 오차로 생긴 미세한 차이가 승패를 가르지 않게 합니다.

| 모드 | A 승 | B 승 | 동점 |
|---|---|---|---|
| 모드 1 | A | B | 판정 불가 |
| 모드 2 | Cross | X | UNDECIDED |

판정 로직은 하나이고, 모드별 표(`MODE1_LABELS`, `MODE2_LABELS`)로 출력 이름만 바꿉니다.

### 2-5. 검증과 오류 처리
- **모드 1:** 한 줄씩 검증합니다. 숫자 개수가 3개가 아니거나 숫자로 변환할 수 없는 값(`nan`, `inf` 포함)이 있으면 안내 문구를 출력하고 **그 줄만** 다시 입력받습니다.
- **모드 2:** 패턴 키는 정규표현식 `^size_(\d+)_(\d+)$`로 해석해 N을 추출하고 `size_N` 필터를 선택합니다. 키 형식 오류, 필터 없음, `input`/`expected` 누락, 크기 불일치, 알 수 없는 라벨은 모두 **해당 케이스만 FAIL**로 처리하고 이유를 기록합니다. 파일이 없거나 JSON 문법이 깨져도 안내 문구를 출력하고 정상 종료합니다.
- **실패 원인 3분류:** 결과마다 원인을 기록합니다.
  - **데이터/스키마:** 검증 단계에서 막힘
  - **수치 비교:** 점수 차이가 epsilon 미만이라 UNDECIDED
  - **로직:** 판정이 expected와 다름

### 2-6. 성능 측정 방법
`time.perf_counter()`로 `mac()` 호출 구간만 측정합니다(입력, 출력, 파일 읽기 제외). 첫 호출은 캐시와 인터프리터 준비 때문에 2~3배 느리므로 워밍업 1회를 측정에서 제외하고, 이후 **10회 반복 평균**을 ms로 출력합니다. data.json에 3×3 필터가 없어서, 3×3은 프로그램 안에서 십자가 행렬을 생성해 측정합니다.

## 3. 결과 리포트

### 3-1. data.json 분석 결과

| 케이스 | expected | Cross 점수 | X 점수 | 판정 | 결과 |
|---|---|---|---|---|---|
| size_5_1 | X | 0.9 | 0.8999999999999999 | UNDECIDED | FAIL |
| size_5_2 | Cross | 8.9 | 0.1 | Cross | PASS |
| size_13_1 | X | 0.3 | 14.700000000000008 | X | PASS |
| size_13_2 | Cross | 7.499999999999997 | 7.5 | UNDECIDED | FAIL |
| size_25_1 | X | 4.9 | 4.899999999999999 | UNDECIDED | FAIL |
| size_25_2 | Cross | 52.9 | 0.1 | Cross | PASS |

**전체 6건 / 통과 3건 / 실패 3건** (실패 원인: 수치 비교 3건)

### 3-2. FAIL 케이스 원인 분석

**1) 분류: 실패 3건 모두 "수치 비교" 단계에서 걸렸지만, 근본 원인은 데이터(필터 가중치 설계)입니다.**

세 케이스 모두 정답 필터와 오답 필터의 점수가 **수학적으로 정확히 같도록** 필터 값이 설정되어 있습니다.

| 케이스 | 정답 필터 점수 | 오답 필터 점수 | 계산 결과 |
|---|---|---|---|
| size_5_1 (X 패턴) | X 필터: 0.1 × 9칸 = 0.9 | Cross 필터: 중앙 1칸 × **0.9** = 0.9 | 0.8999999999999999 vs 0.9 |
| size_13_2 (Cross 패턴) | Cross 필터: 0.3 × 25칸 = 7.5 | X 필터: 중앙 1칸 × **7.5** = 7.5 | 7.499999999999997 vs 7.5 |
| size_25_1 (X 패턴) | X 필터: 0.1 × 49칸 = 4.9 | Cross 필터: 중앙 1칸 × **4.9** = 4.9 | 4.899999999999999 vs 4.9 |

오답 필터의 **중앙 한 칸**에만 큰 값(0.9, 7.5, 4.9)이 들어 있습니다. 십자가와 X는 중앙 1칸만 겹치기 때문에, 그 한 칸의 값이 정답 필터의 점수 전체와 같아집니다. 결국 이 필터들은 해당 패턴에 대해 **판별력이 0**입니다.

**2) 계산 결과가 미세하게 다른 이유는 부동소수점 오차입니다.**

0.1, 0.3 같은 소수는 2진수로 정확히 표현할 수 없어서, 여러 번 누적하면 `0.8999999999999999`, `7.499999999999997`처럼 오차가 쌓입니다. 반면 오답 쪽은 곱셈 1번이라 `0.9`, `7.5`가 그대로 나옵니다. 두 값의 차이(약 1e-15)는 실제 점수 차이가 아니라 저장 방식에서 생긴 잡음입니다.

**3) epsilon 정책이 없었다면 세 케이스 모두 오답이 나왔습니다.**

`>`로 단순 비교하면 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 판정되어 **세 건 모두 expected와 반대**가 됩니다. 이렇게 되면 실패 원인이 "로직 오류"로 잘못 보이고, 덧셈 순서만 바뀌어도 결과가 뒤집힐 수 있는 불안정한 판정이 됩니다. epsilon 정책 덕분에 이 케이스들이 "구별할 수 없음(UNDECIDED)"으로 정직하게 드러났습니다.

**4) 다른 종류의 실패가 0건인 이유**

- **라벨 정규화:** expected의 `+`와 필터 키의 `cross`를 모두 `Cross`로 통일했기 때문에, 표기 차이로 인한 가짜 FAIL이 생기지 않았습니다. 정규화하지 않으면 PASS 3건도 `"cross" ≠ "+"`로 FAIL이 됩니다.
- **스키마 검증:** data.json의 키 형식, 크기, 필드는 모두 정상이었습니다. 검증 로직이 실제로 작동하는지는 `tests/bad_data.json`(오류 4종 포함)으로 따로 확인했습니다 (4절 T8, T9).

**5) 개선 방향**

프로그램을 고쳐서 PASS를 만들 문제가 아닙니다. epsilon을 키우거나 없애면 오히려 잘못된 판정이 나옵니다. 필터의 중앙 가중치를 다른 칸과 같은 수준(예: Cross 5×5 중앙 0.9 → 1.0, X 13×13 중앙 7.5 → 0.3)으로 고치는 것처럼, **데이터 쪽을 수정**해야 정상적으로 판별됩니다.

### 3-3. 성능 분석과 O(N²) 근거

**측정 결과** (워밍업 1회 후 MAC 10회 반복 평균)

| 크기(N×N) | 연산 횟수(N²) | 1차 측정(ms) | 2차 측정(ms) | 2차 1회당(ns) |
|---|---|---|---|---|
| 3×3 | 9 | 0.010210 | 0.004860 | 540.0 |
| 5×5 | 25 | 0.036940 | 0.011670 | 466.8 |
| 13×13 | 169 | 0.158390 | 0.072470 | 428.8 |
| 25×25 | 625 | 0.818120 | 0.265440 | 424.7 |

**1) 시간은 N이 아니라 N²에 비례해서 늘어납니다.**

`mac()`은 바깥 반복 N번 × 안쪽 반복 N번으로, 곱셈과 덧셈을 정확히 N²번 수행합니다. 2차 측정에서 5×5 → 25×25로 N이 5배가 될 때, 연산 횟수는 25배이고 시간은 0.011670 → 0.265440ms로 **22.7배** 늘었습니다. 시간이 N(5배)이 아니라 N²(25배)에 가깝게 증가했으므로 시간 복잡도는 **O(N²)**입니다.

**2) 고정 비용 모델로 정확히 설명됩니다.**

MAC 시간을 `T(N) = a + b·N²`로 보면, a는 함수 호출·크기 검사·초기화처럼 **호출할 때마다 한 번** 드는 고정 비용이고, b는 칸 1개의 처리 비용입니다. 2차 측정의 5×5와 25×25로 계산하면 다음과 같습니다.

- b = (265,440 − 11,670) ns ÷ (625 − 25) ≈ **423 ns**
- a = 11,670 − 25 × 423 ≈ **1,096 ns**

이 식으로 나머지 크기를 예측하면 3×3은 4,903ns(실측 4,860ns), 13×13은 72,575ns(실측 72,470ns)로 **오차가 1% 이내**입니다.

**3) 작은 크기에서 1회당 시간이 큰 이유**

1회당 시간은 `T(N)/N² = a/N² + b`입니다. 고정 비용 a가 3×3에서는 전체 시간의 약 23%를 차지하지만, 25×25에서는 0.4%로 줄어듭니다. 그래서 1회당 시간이 540ns → 425ns로 줄어들며 b(약 423ns)에 수렴합니다. 크기가 커질수록 b·N² 항이 전체 시간을 지배합니다.

**4) 측정 잡음에 대한 관찰**

1차 측정은 1회당 시간이 1,134 → 1,477 → 937 → 1,309ns로 일정하지 않고, 5×5가 3×3보다 1회당 시간이 깁니다. 이것은 고정 비용으로는 설명되지 않습니다. 프로그램 첫 실행 시점의 CPU 절전 상태나 백그라운드 작업 같은 측정 잡음으로 판단됩니다. 그래도 5×5 → 25×25에서 시간이 22.1배 늘어 N² 증가 경향은 유지됐습니다. 마이크로초 단위 측정은 환경에 민감하므로, 10회는 최소 기준이고 반복 횟수를 늘리거나 여러 번 실행해 비교하는 것이 바람직합니다.

**5) NPU와의 연결**

25×25 필터 하나에도 625번의 MAC이 필요하고, 이 프로그램은 이것을 하나씩 순서대로 처리합니다. 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로 연산량이 N²에 비례해 폭증합니다. 수천 개의 MAC을 동시에 처리하는 NPU가 필요한 이유입니다.
